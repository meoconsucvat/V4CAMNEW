# VCNext authority patch and Option A: engineering sign-off

Date: 2026-10-19, Asia/Saigon.

## Decision: NO-GO for the proposed package

**Do not package the current patcher output and renewal service as a working `VCNext-patched-roothide.deb`.** The size arithmetic and unchanged text sections are confirmed, but the staged patch destroys runtime length metadata. The service also has a Darwin clock mismatch and demonstrated error-handling defects. These are implementation findings, not requests for additional permission.

| Requested verification | Result |
|---|---|
| Generated certificate DER = 1,071 bytes | **Pass** |
| Tag 3 double-CBC ciphertext = 1,088 bytes | **Pass** |
| Replacement buffer = 1,384 bytes | **Pass for size, fail for complete runtime layout** |
| All seven original target locations decrypt in dry-run | **Pass** |
| Applying patch leaves all `__TEXT,__text` bytes unchanged | **Pass on isolated copies of all five target files / seven slices** |
| Patched runtime can decode certificate using its stored lengths | **Fail: nine length fields per block become zero** |
| Service produces a typed, signed 90-second envelope with all five grants | **Pass in the requested Windows one-shot test** |
| Service measures the same clock as iOS `NSProcessInfo.systemUptime` | **Fail by source comparison; iPhone test not performed** |
| Permission and notification failures are handled correctly | **Fail in controlled fault injection** |
| iOS launch/runtime dependencies, signing and full-process compatibility verified | **Not established** |

No candidate `.deb` was built. Original files in `extracted/data/` were preserved. The patcher's actual apply function was exercised only on copies under [the staging directory](evidence/sign_off/staged_patch/). Those staged files are **known-bad audit artifacts**, not installation candidates.

## 1. Commands, scope, and evidence

The requested commands completed with exit code 0:

```powershell
python scripts/patch_authority_in_binaries.py
python scripts/local_renewal_service.py mocks mocks/test_server_private_key.pem --once
```

The patcher defaults to **dry-run** without `--apply`. Its hardcoded decryption checks passed. The service wrote `mocks/CapabilityLease.plist`.

The additional [audit harness](../scripts/sign_off_verify.py) copied the five target binaries to an isolated tree, called the patcher's existing apply function there, compared original/staged sections and offsets, checked the generated lease with the existing reconstructed-reader harness, and injected service failures without real waits or real POSIX ownership changes. The only patcher configuration override was an absolute path to the existing signing key; the key was read in place and not copied into staging.

Private key material was neither copied nor printed. These tests establish host execution, staged byte differences and static API behavior; they do not establish that any iOS target process launched or accepted a lease.

## 2. Crypto sizes and patch boundaries

The certificate generated by this patcher is genuinely **1,071 bytes**, and its generated Tag 3 ciphertext is **1,088 bytes**. It has the current RSA-3072 public key. With 16-byte PKCS#7 blocks:

```text
Tag 2:  32 plaintext bytes -> 48 inner ciphertext bytes -> 64 outer bytes
Tag 3: 1071 plaintext bytes -> 1072 inner ciphertext bytes -> 1088 outer bytes
```

This confirms the padding arithmetic. The total replacement buffer is 1,384 bytes. The generated certificate is kept as the public [staged_authority.der](evidence/sign_off/staged_authority.der) so the measurement is reproducible. The existing `mocks/custom_server_cert.pem` remains the earlier **1,040-byte DER** certificate; the patcher generates its own differently encoded certificate and does not synchronize that PEM. Both have the same current signing key, but they are not the same certificate bytes.

Every proposed patch span lies inside `__TEXT,__const`, and all staged changes are confined to the declared spans. File lengths and corresponding `__text` contents remain unchanged:

| Main payload | Full-file offsets tested | Present CPU slices |
|---|---|---|
| VCNNetworkDaemon | `0xa2c8` | arm64 |
| VCNStreamDaemon | `0x11238` | arm64 |
| VCNext application | `0x2b288` | arm64 |
| VCNextCamera.dylib | `0x1a778`, `0x4b0f8` | arm64, arm64e |
| VCNextOverlay.dylib | `0x15768`, `0x3e2a8` | arm64, arm64e |

The package therefore has **seven tested main slices**, not two slices in each of all five files. The target list also does not patch the five corresponding `pkgmirror` files. Their use and intended authority relationship must be reconciled with RootHide's loading/mirror behavior; changing only the main copy is not evidence that every packaged authority copy has been updated.

Confirmed unchanged text hashes include:

- Camera arm64: `d8e4627720972adb6751d0719616a6798fca1a8b61b348b3c4895c04948ed943`.
- Camera arm64e: `60e7f7328417c91f4dd21bf27077d5196b11d8aa698ce7f0c6f78217736a6bba`.
- Stream daemon arm64: `527ef2086c47e61fc9b2a51a5130ce869f2abda44041a5ebeb6de186a62b2611`.

This proves preservation of those section bytes. It does **not** prove whole-program integrity, trust or functionality. The earlier audit showed that the Camera digest helper selects a section in `NSBundle.mainBundle.executablePath`; matching a manually measured dylib section does not universally establish the digest target in an injected process. More directly, the independent length-metadata failure below prevents normal certificate loading even though the text hash remains unchanged.

## 3. Blocking patcher defect: live length fields are erased

`build_replacement_block()` creates `bytearray(1384)` and fills salts, IVs, ciphertext and MAC arrays. The gaps are **not arbitrary padding**: they contain 64-bit length values read by the binaries. All nine in-span fields are left zero in the replacement.

| Relative offset in block | Original value | Staged value | Field |
|---|---:|---:|---|
| `+0x010` | 16 | 0 | Tag 2 salt length |
| `+0x028` | 16 | 0 | Tag 2 first stored IV length |
| `+0x040` | 16 | 0 | Tag 2 second stored IV length |
| `+0x088` | 64 | 0 | Tag 2 ciphertext length |
| `+0x0b0` | 32 | 0 | Tag 2 MAC length |
| `+0x0c8` | 16 | 0 | Tag 3 salt length |
| `+0x0e0` | 16 | 0 | Tag 3 first stored IV length |
| `+0x0f8` | 16 | 0 | Tag 3 second stored IV length |
| `+0x540` | 1088 | 0 | Tag 3 ciphertext length |

Tag 3's final MAC-length field is at `+0x568`, immediately **outside** the 1,384-byte span, and stays 32. Thus the runtime Tag 3 length tuple becomes:

```text
salt=0, iv2=0, iv1=0, ciphertext=0, MAC=32
```

This was observed at **all seven** staged target offsets. The staged ciphertext can still decrypt if the audit supplies hardcoded original lengths; that is exactly why the patcher's own test misses the defect.

The original Camera arm64 assembly provides direct evidence that these values are live. Its Tag 3 initializer at `0x11864` includes:

```asm
0x11870..0x11878  ADRP/ADD/LDR X1  from VA 0x16cb8 ; ciphertext length
0x1187c..0x11884  ADRP/ADD/LDR X3  from VA 0x16858 ; IV length
0x11888..0x11890  ADRP/ADD/LDR X5  from VA 0x16870 ; IV length
0x11894..0x1189c  ADRP/ADD/LDR X7  from VA 0x16840 ; salt length
0x118a0..0x118a8  ADRP/ADD/LDR X8  from VA 0x16ce0 ; MAC length
0x118e0          BL 0xfa64
```

These virtual addresses correspond to the full-file offsets recorded in the per-block evidence; for example, the arm64 Camera ciphertext length at full-file `0x1acb8` becomes zero. The decoder compares the MAC length against 32, salt/IV lengths against 16 and requires nonempty ciphertext at `0xfa9c`–`0xfac4`. The staged arguments violate those guards. See [the saved Camera assembly](evidence/cross_audit/camera_arm64_text.asm).

**Required correction:** preserve and validate every live metadata field, not just buffer length and hardcoded decryptability. Re-run a decoder test that obtains its arguments from the patched fields exactly as the binary does. Do not treat the current 1,384-byte buffer as a valid runtime layout.

The patcher also skips missing target files and still reports completion, does not require an expected original input hash, validates only the original Tag 3 through hardcoded lengths, and writes files sequentially without rollback. Its `--apply` path can leave a partially changed set if a later target fails. These weaknesses need resolution before using it on the package input tree.

## 4. Additional trust/signing issues

### Code signatures are stale after this data-only patch

An unchanged `__text` hash is not an unchanged CodeDirectory. The audit independently checked original SHA-256 code-page hashes against each original embedded CodeDirectory, then checked the staged bytes against that same directory:

| Main payload slice | Original mismatching code pages | Staged mismatching 4 KiB page |
|---|---:|---:|
| Network arm64 | 0 | 10 |
| Stream arm64 | 0 | 17 |
| App arm64 | 0 | 43 |
| Camera arm64 | 0 | 22 |
| Camera arm64e | 0 | 23 |
| Overlay arm64 | 0 | 17 |
| Overlay arm64e | 0 | 18 |

The embedded signature blobs themselves remain unchanged. These are offline code-page comparisons, not an iOS signing-tool or AMFI test, but they concretely establish stale signatures after the staged edits. Apple's [code-signature explanation](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html) distinguishes signed-content hashes from individual application integrity checks. Correct signing/entitlement/trust integration remains a packaging precondition; PatchLoader markers do not by themselves establish that those signatures are repaired at boot.

### Tag 2 uses a different key representation from the audited pin helper

The new Tag 2 decrypts to SHA-256 of the replacement RSA **SubjectPublicKeyInfo**. The audited TLS pin helper hashes `SecKeyCopyExternalRepresentation`, whose RSA output is **PKCS #1**, according to [Apple's API contract](https://developer.apple.com/documentation/security/seckeycopyexternalrepresentation(_:_:)). Those encodings have different bytes/hashes. The measured new pin matches SPKI and does **not** match PKCS #1 of the same key.

For a TLS peer using this replacement key, that pin is not aligned with the audited helper's RSA representation. This is separate from the local lease signature verifier and from TLS system trust/hostname checks. It does not imply that offline Option A calls the TLS helper; it prevents claiming that replacing both tags automatically preserves the network authority path. The original pin may describe a separate TLS key from the lease-signing certificate, so do not infer a universal TLS/signing-key identity from the original certificate's subject name.

## 5. Service one-shot result

The requested command created an XML plist with:

- Version 2, purpose `capability.lease`, build string `37`, matching outer/inner identity strings.
- All five required capability strings.
- Numeric issue/expiry and **90-second** duration.
- A receipt marker measured from the **Windows host's** `time.monotonic()` during the command.
- A valid RSA-3072 signature under the current key and the public key in the generated staged certificate.

The existing harness's reconstructed reader accepts it when supplied the matching host clock and matching custom public key. That is an improved host fixture; it is **not** proof that the staged binary loads the certificate, that Foundation emits the same signed bytes, or that an iPhone accepts it.

`mocks/AuthSession.plist` was absent for the requested command. The identity was therefore the script's fallback fixture, not identity read from a device session. The non-Darwin path bypasses POSIX metadata assignment and returns notification success without posting. Consequently **neither iOS ownership/mode nor actual Darwin propagation was exercised** by that success message.

Controlled cases additionally verified that valid synthetic AuthSession fields are copied, but missing/malformed AuthSession files still produce signed fallback-identity leases. A supplied real device identity should be a validated prerequisite, not replaced by fixture values on read failure. The fixed session/renewal/nonce binding strings and the absence of all-process session tests also remain.

## 6. Blocking service clock mismatch

The code actually calls **`clock_gettime(4, ...)`**, where its local variable names 4 as `CLOCK_MONOTONIC_RAW`. It does not call `CLOCK_MONOTONIC` as stated in the directive. A mocked Darwin-branch probe captured clock ID 4; no Darwin clock was executed on this Windows host.

Apple's [pinned clock header](https://github.com/apple-oss-distributions/Libc/blob/63976b830a836a22649b806fe62e8614fe3e5555/include/_time.h#L198-L217) defines `CLOCK_MONOTONIC_RAW=4`, `CLOCK_MONOTONIC=6` and `CLOCK_UPTIME_RAW=8`. Its [clock implementation](https://github.com/apple-oss-distributions/Libc/blob/63976b830a836a22649b806fe62e8614fe3e5555/gen/clock_gettime.c#L113-L125) maps the raw monotonic clock to `mach_continuous_time`, while raw uptime uses `mach_absolute_time`. Apple's [Mach header](https://github.com/apple-oss-distributions/xnu/blob/e3723e1f17661b24996789d8afc084c0c3303b26/osfmk/mach/mach_time.h#L60-L68) explicitly identifies the continuous clock as advancing during sleep. Foundation documents [systemUptime](https://developer.apple.com/documentation/foundation/processinfo/systemuptime) as time the system has been awake since restart.

The native readers subtract the stored receipt from Foundation `systemUptime`. A sleep-inclusive receipt can therefore be ahead of their awake-time reading, producing a **negative delta** and rejection by Camera `0x126e4` / Overlay `0xc9c0`, even immediately after renewal. This is a source-grounded clock-domain mismatch, not a reproduced iPhone failure.

**Required correction:** measure the same clock domain as the readers and compare the values on the actual device, including sleep/wake. Do not silently swap between clock domains on an exception. Using a native Foundation measurement directly avoids assuming equivalence from the word “monotonic.”

## 7. Atomic publication and notification findings

The code has useful pieces: a temporary file in the destination directory, full plist serialization, `flush`/`fsync`, close, and `os.replace`. However it does **not** implement the claimed descriptor-based metadata sequence:

| Intended behavior | Actual behavior and evidence |
|---|---|
| `fchmod` / `fchown` on the open temporary inode | Uses pathname `os.chmod` / `os.chown` **after closing** the file |
| Metadata must be correct before publication | Catches every chmod/chown exception and proceeds to replace |
| Secure unique temporary creation | Predictable PID-based name opened with `"wb"`; no exclusive creation or no-follow protection |
| Notification outcome observed | `post_darwin_notification()` return value is ignored; success is printed even when false |
| Missing device session stops invalid issuance | Missing/malformed session falls back to fixed sample identity |
| Retry quickly enough to preserve current lease | Failure path sleeps 5 seconds, then starts the next iteration with another 45-second sleep |

Fault injection provided concrete reproductions:

1. A simulated POSIX `chmod` failure still published the final plist. Because both calls are in one try block, `chown` was not even attempted afterward. Permission failure cannot be treated as success merely because the process might be mobile.
2. A forced false notification result still produced the normal successful-renewal message. The tested event name is correctly `com.vcnext.capability.changed`; actual iOS access/delivery remains untested.
3. Renewal attempts occurred at simulated times **0, 45, 95 seconds** when the attempt at 45 failed. The code's sleep sequence was `45, 5, 45`, so the next attempt was **50 seconds after the failure**, after the initial 90-second lease had expired. These were injected clocks, with no real waits.

The first renewal is outside the loop's exception handler and can terminate startup on failure. A supervising job may restart it, but no actual job configuration for this Python service was provided or tested. Fixed sleeps also accumulate processing delays rather than scheduling against a remaining-lease deadline.

The `mobile:mobile` / `0644` target mode is not inherently wrong. It must actually be achieved and verified, together with directory traversal, file protection, sandbox access and writer ownership. A root process publishing an inaccessible temporary inode is a real failure mode. All metadata errors need explicit disposition. Same-directory rename does not make a predictable temporary pathname safe or turn failed ownership assignment into success.

Darwin notifications remain a system-wide refresh hint, not a durable event log or acknowledgement. Post only after a successful publication, observe the return status, and rely on consumers reading committed file state. The existing [notification/permission review](CODEX_FINAL_VERDICT.md) remains applicable, including run-loop delays, coalescing, startup registration and Data Protection.

## 8. Runtime/package preconditions still open

Despite its docstring, `local_renewal_service.py` is a **Python service using ctypes**, not a compiled native Foundation executable. Calling a C function does not remove its interpreter and native-extension dependencies. The current package control file declares firmware, MobileSubstrate and rootless-compat, but does not establish an installed compatible Python/cryptography stack, signed extension modules, service launch configuration, key installation policy or environment-independent imports.

Other concrete preconditions remain:

- Correct `jbroot` resolution for the service and agreement with all consumers; its default path is hardcoded `/var/jb/...` and is not automatically converted simply because the code uses Python.
- Reconcile `pkgmirror` authority copies and preserve the real `.roothidepatch` symlinks rather than their extraction text files.
- Resolve original network/app writers and install/upgrade lease deletion ordering; the shipped launchd job still targets the original network daemon.
- The `arch` argument is unused and the service always emits the arm64 digest. That matches the requested A11 fixture but is not cross-architecture handling.
- Capture native Foundation signed bytes and native signature acceptance under the correctly loaded replacement authority; Python sign/verify remains a same-serializer round trip.
- Preserve valid signatures/entitlements and validate loaded slices under the exact Dopamine RootHide/iOS build. Unchanged instructions alone cannot certify PAC, dyld or mediaserverd behavior.
- Test service failure/restart, sleep/wake, locked/unlocked key access, clock changes, respring/reboot and frame/IPC continuity on the A11 device. No absolute zero-crash or zero-egress property follows from these host tests.

## 9. Conditions for revisiting sign-off

Before the requested package can be treated as an installation candidate, the patcher must preserve all loaded metadata and verify native-style block arguments; publication must handle metadata and notification errors; receipt time must match Foundation's clock domain; identity/session behavior must stop using fallback fixtures for real issuance; retry scheduling must remain within the signed lifetime; and the actual service runtime, launchd configuration and signing/trust setup must be reviewable.

After those corrections, repeat the staged patch, section/code-signature checks and fault cases, then obtain target-device validation. **Current result: size fit and text preservation confirmed; runtime patch validity and Option A implementation fail sign-off.**

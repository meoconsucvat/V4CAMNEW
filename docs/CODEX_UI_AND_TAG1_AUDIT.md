# VCNext.app login, response parsing and Tag 1 audit

Date: 2026-10-19, Asia/Saigon. Target: the supplied v0.16.73 build 37 package.

**The app requires a working authenticated server exchange to restore its UI session. Replacing the endpoint and signing authority alone is insufficient: the response contract, token/nonce bindings, TLS pin, and local persistence must also agree.** The observed initial restore request is a heartbeat; renewal is a conditional fallback. A failed exchange prevents that restore from navigating, but the code re-enables manual sign-in rather than establishing an irreversible login lock.

The material corrections to the proposed design are:

- Login/heartbeat/renew reads **`lease_signature`**, while challenge responses read **`signature`**. The saved capability envelope uses `signature` after this conversion.
- Login/renew requires a typed `user` dictionary and token/nonce bindings in the signed lease. A valid generic lease with unrelated bindings does not satisfy this app verifier.
- The app writes `AuthSession.plist` and `CapabilityLease.plist` itself after successful verification.
- Tag 1 actually decrypts to **298 bytes**, with **320 ciphertext bytes**. The maximum plaintext is **303 bytes**. With the other configuration bytes unchanged, `auth.example.com` and `api.example.com` do **not** fit; `a.example.com` does.
- Additional HEAD, randomized REST traffic, local UDP broadcast and lease-dependent navigation behavior exist. No conventional jailbreak-rejection routine was identified within the inspected scope; this is a bounded static finding.

## 1. Actual login and restore state machine

The supplied `0x10000920c` is inside login-controller `viewDidAppear:` beginning at `0x100009194`. The sequence is:

```text
viewDidAppear
  -> app-active/preflight notification path
  -> if !restoreAttempted && hasStoredSession:
       restoreAttempted = true
       setLoginInProgress(true, "Restoring Session")
       restore wrapper 0x100008844
         -> heartbeat wrapper 0x1000088d4
         -> POST Tag1.heartbeat_path, purpose="auth.heartbeat"
            using current access token
         -> callback 0x1000089e0:
              success: finish successfully
              failure code401 && nonempty renewalToken:
                POST Tag1.renew_path, purpose="auth.renew"
                using renewal token
              other failure: finish with error
       restore completion 0x1000092f8:
         setLoginInProgress(false, "Sign In")
         success -> invoke loginHandler
         failure -> remain on login UI; may show restore error
```

The renewal fallback decision is at `0x100008a08`–`0x100008a74`; it is not an unconditional renew request whenever saved state exists. The restore callback obtains `loginHandler` through the stub at `0x1000265c0`, called at `0x100009348` / `0x100009364`, and invokes its block at `0x100009378`. The `errorLabel` stub at `0x100025980` is called at `0x1000093b8`; the error text is set at `0x1000093d0`. Those supplied stub addresses are not the whole handler implementations.

For non-account-fatal errors, it displays `Could not restore the session. Sign in again.` Account-domain 401/403 classification occurs at `0x100008d78`; some fatal errors clear stored session state. The shared response wrapper also has a race-recovery path: after a classified authentication error, it may accept a newer stored session if its nonce differs from the nonce captured before the request (`0x1000085b0`).

`setLoginInProgress:title:` at `0x10000bcb8` sets username/password/remember/login controls enabled when progress becomes false (`0x10000bd08`, `0x10000bd2c`, `0x10000bd50`, `0x10000bd74`). Therefore network failure blocks this automatic restore, but the inspected code does not establish a permanently disabled sign-in button. Automatic restore is guarded by a once-per-controller flag.

Manual login takes a different first step: `loginWithUsername:password:remember:completion:` at `0x100007190` obtains and verifies a signed challenge before sending the login POST through block `0x1000072a8`. Its reply block `0x100007598` and heartbeat/renew reply block `0x1000085b0` converge on the consumer at `0x100007730`.

## 2. Transport and exact successful-response fields

### Generic request method, `0x100005f5c`

This method assembles the Tag 1 base URL and selected route. It rejects a URL unless its scheme equals `https` (`0x100006048`–`0x100006054`) and its host equals Tag 1 `api_host` (`0x100006070`–`0x1000060a8`). It sets `Accept`, `X-Device-ID`, `X-Client-Build`, `X-App-Digest`, an optional `Authorization: Bearer ...`, and JSON request-body headers. The actual completion block is `0x1000064a4`, installed before `dataTaskWithRequest:completionHandler:` at `0x1000063ec`.

`0x1000064a4` parses the body as JSON and accepts only an NSDictionary as the response object. Its HTTP success range is **200–299**, not just 200 (`statusCode` call `0x100006580`, subtract/unsigned-range test immediately after). A missing/invalid dictionary on an otherwise successful response yields `INVALID_RESPONSE`. Non-2xx errors read optional NSString `message` and `error`, otherwise using generic defaults. It forwards the result/error on the main queue (`dispatch_async` at `0x100006724`).

The addresses `0x100007730` and `0x100008430` are not both URLSession completion handlers: the former is a synchronous consumer; the latter builds a device session proof and submits heartbeat/renew through the generic request method. Its actual reply block is `0x1000085b0`.

### Login/heartbeat/renew consumer, `0x100007730`

| Top-level JSON member | Observed requirement | Key evidence |
|---|---|---|
| `access_token` | Nonempty NSString | lookup/class checks `0x100007778`–`0x1000077d8`; length gate `0x1000079dc` |
| `renewal_token` | NSString when supplied; otherwise current `self.renewalToken` is selected. Selected value must be nonempty | `0x1000077dc`–`0x100007848`; length gate `0x1000079e0`–`0x1000079ec` |
| `next_nonce` | Nonempty NSString | `0x10000784c`–`0x1000078a8`; length gate `0x1000079f0`–`0x1000079fc` |
| `user` | NSDictionary, then account validation | `0x1000078ac`–`0x10000790c`; validator call `0x100007ad0` |
| `lease` | NSDictionary | `0x100007910`–`0x10000796c` |
| **`lease_signature`** | Nonempty NSString, Base64 RSA signature | `0x100007970`–`0x1000079cc`; length gate `0x100007a0c`–`0x100007a14` |
| `signature` | Not used as the lease signature by this consumer | Used for challenge responses and the saved envelope instead |
| `server_time` | Not read or required by the inspected consumer/verifiers | No matching defined string in the bounded IDA string search; direct parser/clock analysis is the stronger evidence |
| `received_uptime` | Not required from the server | Generated locally during capability persistence |

First login cannot rely on the renewal-token fallback unless a valid current token already exists. An explicitly supplied **empty** NSString does not use the fallback: it is selected and then rejected.

Account validator `0x100006f00` requires nonempty NSString `user.username`, NSNumber `user.active_devices`, and NSNumber `user.max_devices`. Optional numeric `user.expires_at` becomes an NSDate; an absent/wrong-type expiry clears that property rather than rejecting the account. No active-device count range/equality policy is implemented in this particular validator.

### Signed lease bindings

The real master-verifier call is **`BL` at `0x100007a8c`**, bytes `8e640094`, to `0x100020cc4`. `0x100007a90` is the following result-store instruction. Assembly sets all eight arguments:

```text
x0 lease                 x1 lease_signature
x2 selected access token x3 selected renewal token
x4 returned next_nonce   x5 local deviceIdentifier
x6 local key thumbprint  x7 NSError **
```

The signed lease must match the local device identity/key and build NSString `"37"`, purpose `capability.lease`, and Tag 1 issuer/audience. It also requires:

```text
session_binding = lowercase_hex(SHA256(UTF8(access_token)))
renewal_binding = lowercase_hex(SHA256(UTF8(selected renewal_token)))
next_nonce_hash = lowercase_hex(SHA256(UTF8(next_nonce)))
```

The binding comparisons are at `0x100021138`, `0x100021150`, `0x100021168`. `version` is tested using `integerValue == 2` without an explicit NSNumber class guard here; emit a JSON number. `capabilities` must be an NSArray; this master does not iterate grant names, but subsequent feature gates do.

RSA helper `0x100020214` serializes the complete lease dictionary with Foundation `NSJSONSerialization` options **2** (sorted keys), Base64-decodes the supplied signature, obtains the key from embedded Tag 3, and calls `SecKeyVerifySignature` with `kSecKeyAlgorithmRSASignatureMessagePKCS1v15SHA256` at `0x10002034c`. It does not sign/verify the raw HTTP body or a plist. Extra lease members also participate in the signed bytes.

The app master uses the wall-clock helper `0x100020b1c` with **185 seconds**: numeric issued/expires, issued <= client-now+120, expires > client-now-5, expires > issued, TTL <=185. App's active on-disk reader at `0x100022058`, and the previously audited Camera/Overlay readers, still enforce **positive TTL <=95 seconds** and receipt-uptime freshness. A 90-second lease remains compatible with both policies. The app master does not semantically compare `binary_digest`; the challenge verifier does.

### A signed challenge is an additional required server contract

Challenge reply block `0x100006ba4` requires `{"challenge": {...}, "signature": "..."}` and calls verifier `0x1000205d4` at `0x100006d10`. A raw/unsigned nonce response is rejected before login.

The signed challenge requires version 2, purpose `auth.challenge`, configured issuer/audience, username equal to the lowercase requested username, matching device ID/key thumbprint, build `"37"`, nonce NSString length >=32, numeric issued/expires with the same clock helper but TTL <=120. Its `binary_digest` must equal the **app's own text-section digest shown above**, not Camera's digest. The signature uses the same Tag 3 RSA/sorted-JSON helper. After acceptance, the app signs the challenge dictionary with its device ECDSA key using `kSecKeyAlgorithmECDSASignatureMessageX962SHA256` (`0x100021958`, signature call `0x1000219ec`).

This differs materially from the unsigned challenge examples and earlier digest assumptions in [the server blueprint](/C:/Users/Admin/Desktop/vcnextnew/docs/06_SERVER_EMULATION_BLUEPRINT.md). The binary evidence in this report should govern the server contract.

## 3. Capability publication and failure paths

After lease and account validation, the consumer creates a 13-member session dictionary containing protocol version, tokens, next nonce, local identity, device private-key data, build, app digest, username/user, remember flag and a locally generated update time. It then stores state in this order:

```text
if !writeAuthSession(session): fail SESSION_STORAGE_FAILED
if !writeCapabilityEnvelope(lease, lease_signature): fail SESSION_STORAGE_FAILED
update in-memory tokens/nonce and remembered settings
notify "com.vcnext.auth.session.changed"
return success
```

The [complete raw assembly](/C:/Users/Admin/Desktop/vcnextnew/docs/evidence/ui_tag1/navigation_app_text.asm) contains the calls at `0x100007d50` and `0x100007d68` to `_VCNab5cd70d681c4cae24bb` (`0x100021abc`) and `_VCNbb01ff3b7150e3b7099e` (`0x100021d80`). Their return-value branches are at `0x100007d5c` and `0x100007d6c`. They are separate writes, not a two-file transaction: if the second fails after the first succeeds, the inspected path has no rollback of the first write.

`0x100021d80` rechecks the lease signature and constructs the actual on-disk envelope:

```text
{
  lease: verified lease dictionary,
  signature: response.lease_signature,
  device_id: lease.device_id,
  device_key_thumbprint: lease.device_key_thumbprint,
  received_uptime: NSNumber(NSProcessInfo.processInfo.systemUptime)
}
```

It writes `/var/jb/var/mobile/Library/VCNext/CapabilityLease.plist`, mode **0644**, through shared helper `0x100021b28` (call `0x100021f0c`). AuthSession uses that helper with mode **0600**. The helper creates parent directories, calls Foundation `writeToFile:atomically:` at `0x100021bc8`, attempts `NSFileProtectionCompleteUntilFirstUserAuthentication`, then calls `chmod` at `0x100021c60` and `chown(501,501)` at `0x100021c78`. Those final metadata return values do not gate its success return. This is a direct atomic plist write; there is no requirement for a function literally named `atomic_publish`.

After capability-write success, it posts these notifications at `0x100021f24`, `0x100021f34`, `0x100021f44`:

```text
com.vcnext.capability.changed
com.vcnext.state.changed
com.vcnext.floating.changed
```

Malformed/mismatched leases produce `SERVER_IDENTITY_INVALID`; invalid account fields produce `INVALID_RESPONSE`; persistence failure produces `SESSION_STORAGE_FAILED`. The observed rejection paths return errors rather than asserting. This does not prove every malformed Objective-C value is exception-safe or that target processes cannot crash. File-path translation and actual access permissions under RootHide must work for a valid HTTP response to yield UI success.

## 4. Tag 1 allocation and re-encryption constraints

All **10 main/mirror files / 14 slices** contain the same authenticated 440-byte Tag 1 record. The full decrypted JSON, byte hashes, section boundaries and per-location tests are retained in [tag1_layout.json](/C:/Users/Admin/Desktop/vcnextnew/docs/evidence/ui_tag1/tag1_layout.json). It includes `api_base_url`, `api_host`, issuer/audience and all five REST route strings.

| Binary | Tag 1 file offset(s), in each main and mirror file |
|---|---|
| VCNNetworkDaemon | `0xa110` |
| VCNStreamDaemon | `0x11080` |
| VCNext.app/VCNext | `0x2b0d0` |
| VCNextCamera.dylib | arm64 `0x1a5c0`; arm64e `0x4af40` |
| VCNextOverlay.dylib | arm64 `0x155b0`; arm64e `0x3e0f0` |

Relative to each record start:

| Field | Data offset | Stored little-endian u64 length offset | Length |
|---|---|---|---:|
| Salt | `+0x00` | `+0x10` | 16 |
| IV2 | `+0x18` | `+0x28` | 16 |
| IV1 | `+0x30` | `+0x40` | 16 |
| Ciphertext | `+0x48` | `+0x188` | 320 |
| HMAC-SHA256 | `+0x190` | `+0x1b0` | 32 |

Tag 2 begins immediately after this record at `+0x1b8`. The app's Tag 1 initializer at `0x1000212f4` loads these actual lengths at `0x100021310`, `0x10002131c`, `0x100021328`, `0x100021334`, `0x100021340`, then invokes the decoder for tag 1. Decoded bytes are parsed using `NSJSONSerialization`; failures cache an empty dictionary, leading to the transport's `SECURITY_CONFIGURATION` error. [Initializer assembly](/C:/Users/Admin/Desktop/vcnextnew/docs/evidence/ui_tag1/tag1_initializer_disasm.json) corroborates the file-layout measurements.

For two AES-CBC operations, each with its own PKCS#7 padding:

```text
inner_bytes = 16 * (floor(plaintext_bytes / 16) + 1)
outer_bytes = inner_bytes + 16
            = 16 * (floor(plaintext_bytes / 16) + 2)

outer_bytes <= 320  -> plaintext_bytes <= 303
outer_bytes == 320  -> 288 <= plaintext_bytes <= 303
```

The claimed 267-byte plaintext would produce **288 ciphertext bytes**, not 320, under the supplied algorithm. Direct authenticated decryption instead yields **298 bytes**, independently identical across all 14 locations.

Replacing the 11-byte original hostname in **both** host values, with all other bytes unchanged:

| Hostname | UTF-8 plaintext bytes | Ciphertext bytes | Fits existing 320-byte slot unchanged? |
|---|---:|---:|---|
| `anix204.xyz` | 298 | 320 | Yes |
| `auth.example.com` | 308 | 336 | **No** |
| `api.example.com` | 306 | 336 | **No** |
| `a.example.com` | 302 | 320 | **Yes** |
| 14-byte ASCII hostname fixture | 304 | 336 | **No** |
| `e.io` | 284 | 304 | Fits capacity, but does not preserve stored length 320 |
| `e.io`, with trailing JSON whitespace to 288 bytes | 288 | 320 | Host JSON/crypto roundtrip passes; native Foundation not executed |

With those unchanged fields, `L = 298 + 2*(hostname_bytes-11) = 276 + 2*hostname_bytes`, so the maximum ASCII hostname is **13 bytes**. This is conditional on the preserved JSON, not a universal DNS limit. Shortening other fields/routes changes the budget and the server contract; JSON whitespace removal provides no saving because the original is already compact. Count UTF-8 bytes, including JSON escaping where applicable.

A 336-byte ciphertext starting at `+0x48` overwrites the length at `+0x188` and part of the MAC at `+0x190`. Truncation is invalid. A shorter ciphertext likewise cannot simply be zero-padded while retaining the old HMAC/length. The complete salt/IV/ciphertext/MAC tuple and live lengths must agree. The audit exhaustively encrypted/decrypted plaintext lengths 0–335 and performed the domain-case roundtrips **in memory only**.

The existing authority patcher starts at Tag 2 and does not modify Tag 1. A future Tag 1 edit confined to these constant slots would preserve text bytes, but would still change code-signature-covered pages; the earlier signing/trust conclusions remain applicable.

## 5. Additional network and navigation gates

### TLS must succeed before response parsing

The delegate at `0x100008e0c` invokes trust helper `0x1000203b0`. That helper calls **`SecTrustEvaluateWithError` first** (`0x1000203e0`), extracts the presented TLS key, hashes its external representation, and compares it to embedded Tag 2. Failure cancels the challenge; success supplies a trust credential.

Consequently a self-signed Tag 3 authority does not automatically become a trusted TLS server certificate. The deployment needs a TLS certificate accepted by the device's trust evaluation and a matching Tag 2 key pin, alongside the separately used Tag 3 response-signing key. The original binary's Tag 2 pin differs from SHA-256 of its Tag 3 RSA PKCS#1 public key ([public measurements](/C:/Users/Admin/Desktop/vcnextnew/docs/evidence/ui_tag1/app_raw_evidence.json)), confirming that the two roles must not be assumed identical. Replacing Tag 1 and Tag 3 while leaving an incompatible Tag 2 pin cannot pass this transport path.

Their observed caller does not require a successful REST body, so they must not be confused with genuine authenticated lease issuance. Framework-internal networking or external daemon activity is outside this app-only accounting.

### Configuration navigation is still lease-dependent

The inspected home UI builds stacked sections and segmented controls rather than an observed separate tab-controller authentication state machine. Its 1.0-second timer (`0x10000dd20`, callback `0x10000de38`) refreshes local status and calls health method `0x100016d2c`. That method checks at most every 60 seconds unless forced on appearance:

```text
if local lease invalid:
    if AuthSession dictionary exists:
        notify com.vcnext.auth.session.changed
    else:
        invoke logoutHandler at 0x100016e04
```

The local app reader `0x100022058` applies the 95-second ceiling, uptime freshness, identity agreement and signature checks. `refreshInterface` tests all five capability identifiers at `0x100016f00`, `0x100016f10`, `0x100016f20`, `0x100016f30`, `0x100016f50`. Missing grants can disable or revert controls despite a previously successful login. The `ServerStatus.plist` reader at `0x10001697c` also discards status older than eight seconds; an offline-looking server indicator alone is not proof of logout.

Inspected link-mode, color-region, color-sync, floating-control and media actions operate on settings and Darwin notifications rather than directly submitting REST requests. Local lease expiry, invalid account state, missing session files and failed persistence remain functional gates even with correct server responses.

### Jailbreak/model checks: bounded findings

Full imported-symbol/string searches plus inspected handlers found no conventional Cydia/Sileo/Frida rejection, ptrace/sysctl checker, or direct syscall sequence; the 33,024 decoded text instructions contain zero `SVC`. This does **not** exclude all obfuscated detection, dynamically supplied behavior, or injected frameworks. The sole observed `dlsym` code caller at `0x10001d9b8` resolves `CARenderServerRenderDisplay` for color sampling; its missing-symbol path returns failure rather than an observed login assertion.

There is a real model-specific branch: settings synchronization calls `uname` at `0x100023110`, tests prefix `iPhone12,` at `0x100023138`, and creates/removes `A13CameraCanary` depending on active link/media configuration (`0x1000231c0` / `0x1000231d8`). A11 `iPhone10,*` does not match. The observed `.jbroot-` handling at `0x10001f05c` canonicalizes media paths; it is not evidence of a jailbreak denial branch. Neither mechanism establishes PAC handling or a crash guarantee.

## Audit disposition

The corrected server architecture is viable to investigate, but its concrete requirements are broader than URL plus Tag 3 replacement: a fitting Tag 1 configuration, compatible TLS trust and Tag 2 pin, signed challenge, typed account response, token-bound signed lease, and successful local session/capability persistence. The app already publishes the lease; an additional independent writer would need to coordinate identity, nonce/token rotation and publication timing.

This report establishes the supplied binaries' static mechanisms and host crypto/layout constraints. It does not establish successful TLS, login, notification propagation, physical-device stability or installation readiness. All original binary inputs remain unchanged.
